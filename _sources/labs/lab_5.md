## Basic Exercise 2 - Hardware Cache Coherence - 30%
Because our NPU directly access memory through AXI without passing through the D-cache, you may encounter cache coherence problem under several situations.  
We provide you some scenarios to think about:

| Scenario | Problem |
|---|---|
| A/B are dirty cache lines newly written by the CPU | The NPU reads the old A/B from DDR |
| C is a clean cache line previously read by the CPU | The NPU completes writing C, but the CPU continues to read the old C |
| C is a dirty cache line modified by the CPU | The old C is later written back, overwriting the NPU's new result |

To solve cache coherence problems without CBO, we use hardware to deal with it.  
This section is a little bit complex, you may need to trace codes of `CPU(I/O to Backend_top)`, `Backend_top`, `dcache_pro`, `(MEM)` in `Platform/hw/srcs/sources_1/imports` to understand how they work and interact with each other. And you may need to modify them or add new modules in the same folder and use `Block Design`.

Here is a guideline of BD: 

For every GEMV operation, the NPU must use the latest A and B values written by the CPU. Once the operation completes, CPU reads of C must return the NPU's results, and older cached values must not overwrite C later. Hardware must provide these guarantees without software cache-maintenance operations in the Lab5 GEMV execution path. You may choose how to coordinate the CPU cache and NPU.  

One possible design is to let the NPU request D-cache writeback or invalidation when needed around its AXI memory accesses. Other hardware approaches are also valid.

After you finish your work, you can still use `systolic_array_test` to test your work. But before you test, make sure you delete or comment all CBO extension use.
```{important}
During testing, we will remove cbo.h before compiling, so you must ensure it compiles without any errors.
```

## Advanced Exercise - Accelerate Convolution - 20%
Now you have a working systolic array that can do GEMV correctly, it's time to **accelerate convolution**.  

We provide `conv.h` with the code used to measure **Counter 2**. You may modify this file to integrate your systolic array and implement your acceleration method. **Keep the Perf Start and Perf End code unchanged and in their original locations.**

### Hints
- **im2col:** One possible approach is to reorganize input patches for matrix-based computation. For the convolution cases in this exercise, you may assume a batch size of 1 and a group count of 1.
- **Tiling:** Consider dividing the computation into smaller tiles when the full workload does not fit the storage available to your design.
- **Input offset:** Quantized convolution includes an input offset. Make sure your accelerated result matches the reference computation, including at padded boundaries.
